# FoT-AMS database preflight report (dry-run findings and corrections)

Project OOP-2026-GP-12 - database `faculty_ams` - written 1 November 2026.

## 0. What this report is based on, and what it is not

* **Inspected:** the files in the project ZIP (SQL scripts, DAOs, models, services, DB configuration, sample data,
  the self-check classes) and the ICT2132 Mini Project PDF.
* **NOT inspected:** your live MySQL database. No MySQL server was reachable from the environment where this
  work was done, so **no SQL script has been executed against MySQL**. Everything below that says "data could be
  affected" is derived from reading the scripts. The first thing to do on your machine is run
  `database/audit_existing_database.sql` (read-only) and look at its FAIL/WARN rows.
* **What was executed:** the Java sources were compiled with `javac --release 17`; the self-check classes were run;
  the demo-data scripts and the verify/audit check conditions were run in an **SQLite emulation** (see section 5).
  SQLite is not MySQL: that run proves name resolution, repeatability and the arithmetic, not MySQL syntax acceptance.
* **Not available and therefore NOT verified:** UGC Commission Circular No. 12-2024 (the site could not be fetched),
  the official B09 timetable and the official assessment criteria of each module. The grade bands in the code and the
  sample courses / assessment schemes in the demo data are **placeholders** and are labelled as such.

### 1.3 Business rules in code that the data must follow

## 2. Part B - the one authoritative schema

`database/schema.sql` defines, in their final shape, the tables read or written by `UserDAO`, `DepartmentDAO`,
`CourseDAO`, `AttendanceDAO`, `MedicalDAO`, `ReportDAO`, `LecturerDAO`, `MarksDAO`, `EvaluationComponentDAO`,
`CourseMaterialDAO`, `StudentDAO`, `StudentProfileDAO`, `StudentResultDAO`, `StudentMaterialDAO`,
`StudentAttendanceDAO`, `StudentMedicalDAO`, `EnrollmentDAO`, `NoticeDAO`, `TimeTableDAO`, `StudentNoticeDAO`,
`StudentTimetableDAO`, `LecturerAccessDAO`, `TechnicalLookupDAO`, `TechnicalDashboardDAO`:

`departments, users, lecturers, students, courses, notices, notice_reads, timetables, enrollments, course_component,
session_attendance, medical, evaluation_component, component_marks, marks, course_materials, schema_migrations`.

The Lecturer and Undergraduate modules use **the same** `marks` and `course_materials` tables with **one** layout
(`marks`: marksid, student_id, course_id, obtainMarks, finalMarks, grade, isEligible, overall_mark, grade_points,
published, published_at; `course_materials`: materialID, courseID, description, notes, referenceText). The only
conflict is with a *legacy* table of another layout that may exist in an old database; that is handled by a stop +
manual recovery plan, never by renaming.

No table was renamed, no parallel table was created.

## 3. Part C - migration order

Fresh install:
`schema.sql` -> `000` -> `001_notices_timetables` -> `002` -> `003` -> `005` -> `007` -> `009` -> `010`
(demo data, development only) -> `sample_data.sql` -> `001_sample_notices_timetables` -> `004` -> `006` -> `008`.

Existing database: **backup** -> `audit_existing_database.sql` -> `000, 001_notices_timetables, 002, 003, 005, 007, 009, 010`
-> `audit_existing_database.sql` and `verify_assignment_data.sql` again. Demo data only on a throw-away copy.
(Migration `004` needs `009` first; the older note "003, 004, 009" no longer applies. `006` needs `005` + `007`; `008` needs `004`, `006`, `007`.)

Operations that may lose or orphan data are never run automatically:
1. **Incompatible `marks` / `course_materials`** - scripts stop; manual template in `database/manual/`.
2. **Duplicate rows** that block a unique key - the key is skipped with a WARNING; fix the duplicates, run again.
3. **Orphan rows** that block a foreign key - the key is skipped with a WARNING; fix the rows, run again.
4. **Rows violating a CHECK** (marks outside 0-100 ...) - the check is skipped with a WARNING.
